# 작업 규칙

커밋, 브랜치, 기록을 어떻게 남기는지 정리한 문서. 규칙이 바뀌면 이 문서부터 고친다.

## 1. 작업 단위

작업 단위 하나는 "한 문장으로 이유를 설명할 수 있는 변경"이다.

- 기능 하나, 버그 하나, 리팩토링 하나가 각각 별도 단위다.
- 단위마다 GitHub 이슈를 하나 연다. 이슈 번호가 브랜치, 커밋, 기록을 묶는 기준이 된다.
- 작업 중에 다른 문제를 발견하면 지금 브랜치에서 고치지 않고 이슈만 새로 연다. 지금 작업을 막는 문제라면 예외로 같이 고치되, 커밋은 분리한다.

## 2. 브랜치

`main`에는 직접 커밋하지 않는다. 문서 오타 같은 사소한 수정만 예외.

| 접두어 | 용도 | 예 |
|---|---|---|
| `feat/` | 기능 추가 | `feat/12-price-parser` |
| `fix/` | 버그 수정 | `fix/27-duplicate-run` |
| `refactor/` | 동작 변화 없는 구조 개선 | `refactor/31-collector-interface` |
| `docs/` | 문서만 | `docs/adr-task-queue` |
| `chore/` | 설정, 의존성, 도구 | `chore/docker-compose` |

형식은 `<접두어>/<이슈번호>-<짧은-영문-설명>`. 이슈가 없으면 번호는 뺀다.

병합은 PR로 하고 Merge commit 방식을 쓴다. Squash로 합치면 잘게 나눈 커밋 이력이 사라지기 때문이다.

## 3. 커밋

### 메시지 형식

```
<타입>(<범위>): <제목>

<본문: 왜 바꿨는지>

Refs: #12, TS-0003
```

- 제목은 한국어, 명사형으로 끝낸다. 50자 안팎, 마침표 없음.
  - 좋음: `fix(parser): 할인가가 있을 때 정가를 저장하던 문제 수정`
  - 나쁨: `fix: 버그 수정`, `feat: 여러 기능 추가 및 리팩토링`
- 본문에는 "무엇"보다 "왜"를 쓴다. 무엇을 바꿨는지는 diff에 있다. 한 줄로 충분하면 한 줄만.
- 범위는 바뀐 영역이다. `collector`, `scheduler`, `api`, `web`, `analysis`, `alert`, `db`, `infra`, `mock-shop`, `docs` 등. 영역이 생기는 대로 추가한다. 여러 영역에 걸치면 생략해도 된다.
- 꼬리말 `Refs:`에는 관련 이슈 번호와 기록 ID를 적는다. 없으면 생략.
- `Co-Authored-By:` 트레일러는 넣지 않는다.
- 호환성을 깨는 변경은 타입 뒤에 `!`를 붙인다. 예: `feat(api)!: 작업 목록 응답 형식 변경`

### 타입

| 타입 | 언제 |
|---|---|
| `feat` | 사용자가 체감하는 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 동작은 그대로 두고 구조만 변경 |
| `perf` | 성능 개선. 전후 측정값을 본문에 쓴다 |
| `test` | 테스트만 추가하거나 수정 |
| `docs` | 문서, 기록 |
| `build` | 의존성, 빌드 설정 |
| `ci` | CI 설정 |
| `chore` | 그 밖의 설정 파일, 스크립트 |
| `style` | 포매팅만. 로직 변화 없음 |
| `revert` | 이전 커밋 되돌림 |

### 쪼개는 기준

- 제목에 "및", "그리고", "+"가 들어가면 쪼갤 수 있다는 신호다.
- 리팩토링과 기능 변경은 같은 커밋에 넣지 않는다. 리팩토링이 필요하면 `refactor` 커밋을 먼저 하고 그 위에 `feat`이나 `fix`를 쌓는다.
- 포매팅과 의존성 추가는 각각 따로 커밋한다.
- 버그 수정은 가능하면 재현 테스트를 먼저 `test` 커밋으로 남기고, 그다음에 `fix` 커밋을 한다. 이력만 봐도 문제를 먼저 재현했다는 게 보인다.
- 시도했다가 버린 접근도 남길 가치가 있으면 커밋한 뒤 `revert`로 되돌린다. 그냥 지우면 그런 시도가 있었다는 흔적이 사라진다. 트러블슈팅 기록에서 두 커밋을 모두 링크한다.
- 각 커밋은 되도록 빌드와 테스트가 통과하는 상태여야 한다. 위의 재현 테스트 커밋은 예외.

## 4. PR

브랜치 하나에 PR 하나. 혼자 작업해도 PR을 만든다. PR 설명이 그 작업 단위의 요약이 된다.

```
## 무엇을
## 왜
## 어떻게 확인했나
실행한 테스트, 직접 확인한 절차, 스크린샷
## 관련
Closes #12 / TS-0003 / ADR-0002
```

## 5. 기록

| 종류 | 언제 쓰나 | 위치 | ID |
|---|---|---|---|
| 개발 일지 | 작업한 날마다. 짧아도 된다 | `docs/devlog/YYYY-MM-DD.md` | 날짜 |
| 트러블슈팅 | 첫 가설이 틀렸거나, 원인이 예상과 달랐거나, 해결에 시도가 두 번 이상 필요했을 때 | `docs/troubleshooting/NNNN-slug.md` | `TS-NNNN` |
| 기술 결정 (ADR) | 대안이 둘 이상 있었고 그중 하나를 골랐을 때 | `docs/adr/NNNN-slug.md` | `ADR-NNNN` |
| 분석 노트 | 데이터를 들여다보거나 알고리즘을 실험했을 때 | `docs/analysis/NNNN-slug.md` | `AN-NNNN` |

- 번호는 종류별로 0001부터 차례로 매긴다.
- 템플릿은 각 폴더의 `_template.md`.
- 새 기록을 만들면 [docs/README.md](README.md) 목록에 한 줄 추가한다.
- 무엇을 어떻게 남기는지는 [record-principles.md](record-principles.md)를 따른다.

### 근거 자료는 그 자리에서 남긴다

해결하고 나서 기억으로 쓰면 원인과 판단 근거가 흐려진다.

- 에러 메시지는 요약하지 말고 원문 그대로 복사한다.
- 실행한 명령어와 그 출력.
- 수치. 응답 시간, 메모리, 처리 건수. 실제로 잰 값만 쓴다.
- 화면 문제는 스크린샷을 `docs/assets/`에 저장한다.

정리는 나중에 해도 된다. 조건에 걸리면 일단 `docs/troubleshooting/`에 파일부터 만들고 자료를 붙여 넣는다.

### 서로 찾아갈 수 있게

- 커밋 꼬리말 `Refs:`에 기록 ID
- 기록 문서의 "관련" 항목에 커밋 해시
- PR 설명에 이슈 번호와 기록 ID

`git log --grep "TS-0003"` 한 줄로 그 문제와 관련된 커밋이 전부 나와야 한다.

## 6. 처음 클론했을 때

커밋 메시지 검사 훅과 메시지 템플릿을 켠다. 클론마다 한 번씩 해야 한다.

```bash
git config core.hooksPath .githooks
git config commit.template .gitmessage
```
