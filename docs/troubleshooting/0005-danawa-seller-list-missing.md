# TS-0005: 다나와 수집이 실행마다 번갈아 "판매처 목록을 찾지 못함"으로 실패

- 날짜: 2026-11-03
- 관련: #46, ADR-0005, ADR-0007
- 상태: 해결

> 요약: 다나와가 상품 페이지를 Next.js로 바꾸면서 옛 페이지와 새 페이지를 요청마다 섞어 내보냈다. 새 페이지에는 판매처 HTML 목록이 없어 판매처 파싱이 실패했다. 새 페이지에서는 페이지 데이터의 priceCompareTab 섹션에서 옛 목록과 같은 기준으로 판매처를 고르게 고쳤다.

## 증상

사용자가 "주기적 실행이 실패한다고 계속 메일 오던데"라고 알려 줬다. GitHub Actions 가격 수집 #255(run 41652173527, 2026-11-03 23:17 KST)의 다나와 수집 단계 로그:

```
run 491 danawa: success (20/20), trigger=schedule
문제: 판매처 목록 파싱 실패 20개
- 18297722 판매처 목록: 판매처 목록(ul.list__mall-price)을 찾지 못함
- 74056484 판매처 목록: 판매처 목록(ul.list__mall-price)을 찾지 못함
...
- 122688356 판매처 목록: 판매처 목록(ul.list__mall-price)을 찾지 못함
걸린 시간: 0:01:19.098916
Healthchecks 신호(fail): 보냄
Error: Process completed with exit code 1.
```

HTTP 응답은 전부 200이었다. 최저가와 판매처 수(JSON-LD)는 저장됐고, 판매처 목록만 비었다.

Neon에서 최근 다나와 실행별로 "판매처 목록" 오류가 난 스냅샷 수와 판매처가 저장된 스냅샷 수를 셌다 (시각은 KST).

```

465 2026-11-03 10:17:35 success 20 20 0
467 2026-11-03 11:17:32 success 20 20 0
469 2026-11-03 12:17:29 success 20 20 0
471 2026-11-03 13:17:30 success 20 0 20
473 2026-11-03 14:17:30 success 20 20 0
475 2026-11-03 15:17:31 success 20 0 20
477 2026-11-03 16:17:36 success 20 20 0
479 2026-11-03 17:17:31 success 20 0 20
481 2026-11-03 18:17:33 success 20 0 20
483 2026-11-03 19:17:32 success 20 20 0

```

10-31 16:17부터 11-03 09:17까지는 모든 실행에서 20개 모두 판매처가 저장됐다. 11-03 10:17부터 실패가 시작됐고, 실패한 실행은 20개 상품 전부 실패, 성공한 실행은 20개 전부 성공이었다.

## 재현 조건

2026-11-03 로컬에서 수집기와 같은 User-Agent로 `prod.danawa.com/info/?pcode=18297722`를 한 번 받았다. 응답 983KB에 `list__mall-price`가 없었다.

같은 주소를 몇 초 간격으로 다시 받으니 옛 페이지(164KB, `list__mall-price` 있음)와 새 페이지가 섞여 나왔다.

```
1 23:59:59 old=1 new=0
2 00:00:08 old=1 new=0
3 00:00:17 old=1 new=0
4 00:00:25 old=1 new=0
5 00:00:34 old=0 new=2
6 00:00:42 old=0 new=2
7 00:00:51 old=1 new=0
8 00:01:00 old=1 new=0
```

응답마다 `PHPSESSID` 쿠키가 새로 나왔다. 수집기는 한 실행 안에서 같은 클라이언트로 20개를 받는데, 실행 단위로 20개가 모두 실패하거나 모두 성공한 것을 보면 실행 안에서는 같은 페이지를 받은 것으로 보인다. 무엇으로 나뉘는지(쿠키, 시각, 서버)는 확인하지 않았다.

## 원인 찾기

| 가설 | 확인 방법 | 결과 |
|---|---|---|
| 차단이나 오류 페이지를 받았다 | 로그의 HTTP 상태, JSON-LD 저장 여부 | 아님. 모두 200이고 최저가는 저장됐다 |
| 다나와 상품 페이지 구조가 바뀌었다 | 로컬에서 받은 HTML 확인 | 맞음. `static.danuri.io/front/pricecompare-pc/_next/...` 스크립트를 쓰는 Next.js 페이지이고, `self.__next_f.push(...)`로 데이터가 들어 있다 |

새 페이지의 데이터에는 React Query의 dehydrated state가 있고, `queryKey: ["productInfo","priceCompareTab",...]`의 `data.sections`에 판매처가 있다. pcode 18297722에서 본 섹션:

```
openMarket 오픈마켓 30
affiliate 백화점/홈쇼핑/종합몰 20
cardCash 카드/현금 동일 전문몰 7
publicSell 일반 전문몰 10
```

항목마다 `shop`, `companyCode`, `rawPrice`, `deliveryPrice`, `isLowest`, `isCash` 등이 있다. 같은 쇼핑몰이 여러 번 나온다(옥션, G마켓 등). JSON-LD `offers.lowPrice`는 800230으로 `isCash`가 아닌 가격 중 최저와 같았다.

## 원인

다나와 상품 페이지 개편. 2026-11-03 10:17 KST 실행부터 새 페이지를 받기 시작했다. 새 페이지에는 수집기가 판매처를 읽던 `ul.list__mall-price`가 없다. 판매처 목록이 비면 수집기는 실행을 실패로 끝내고 Healthchecks에 fail 신호를 보낸다(ADR-0007). 그래서 Actions 실패 메일이 왔다.

## 해결

새 페이지 데이터에서 판매처를 고르는 기준을 옛 목록에 맞췄다. 옛 목록과 새 섹션을 비교해서 정했다.

- 10-31 이후 Neon에 저장된 옛 목록(run 461, 20개 상품)을 보니 판매처마다 한 번씩만 나오고, 현금가가 아닌 가격은 오름차순이고, 현금가는 있으면 마지막에 하나 있었다 (10곳 중 마지막이 현금 13개, 현금 없음 6개, 8곳 중 마지막이 현금 1개).
- 같은 상품을 거의 같은 시각에 옛 페이지와 새 페이지로 받아 비교했다. 처음에는 모든 섹션에서 쇼핑몰별 최저가를 모아 가격순 10곳을 골라 봤는데, 옛 목록에 없는 카드/현금 동일 전문몰 판매처가 들어갔다. 섹션별로 세어 보니 옛 목록은 오픈마켓 4곳, 종합몰 4곳, 카드/현금 동일 전문몰 1곳, 일반 전문몰(현금) 1곳이었다.
- 이 기준으로 새 페이지 4개 상품(5쌍)을 옛 목록과 비교한 결과:

| 상품 | 판매처 수 | 같은 판매처·가격 |
|---|---|---|
| 18297722 (2쌍) | 10 / 10 | 10, 9 |
| 74056484 | 10 / 10 | 9 |
| 20644043 | 10 / 10 | 10 |
| 122688356 | 8 / 8 | 2 |

- 9곳만 맞은 경우는 같은 가격 판매처(846,700원 두 곳, 599,000원 두 곳) 중 어느 쪽이 들어가느냐였다. 옛 페이지도 요청마다 동점 중 다른 판매처를 보여 줬다(18297722의 두 옛 페이지).
- 122688356은 두 페이지의 가격이 달랐다(롯데ON 169,760원 / 167,260원, 플러스 134,300원 / 131,600원). 옛 목록 1위는 139,000원인데 두 페이지의 JSON-LD 최저가는 모두 138,030원이고 새 페이지의 엔코퍼레이션 138,030원과 같다. 옛 목록의 오픈마켓 4곳(알파스캔, 옥션, G마켓, 11번가)이 새 데이터의 오픈마켓 최저 4곳과 다른 이유는 찾지 못했다.

검토한 선택지:

- (a) 새 페이지의 판매처 전부(이 상품은 67곳) 저장: 분석에는 더 낫지만 판매처 행이 6~7배가 된다. ADR-0005 측정(1년 245MB, 10곳 기준)으로 보면 Neon 무료 한도를 넘는다.
- (b) 가격순 10곳: 단순하지만 옛 목록과 구성이 달라 10-24부터 쌓인 데이터와 이어지지 않는다.
- (c) 옛 목록의 섹션별 구성을 따른다: 대부분 같은 목록이 나온다. 선택.

옛 페이지도 계속 나오므로 `ul.list__mall-price`가 있으면 HTML로, 없고 `self.__next_f`가 있으면 새 데이터로 읽는다. "최저가" 배지는 옛 페이지처럼 1위에만, "현금"은 현금가 판매처에 붙인다. 이 선택은 Claude가 했다.

## 배운 것

- 판매처 HTML이 깨질 수 있다고 보고 최저가를 JSON-LD에서 따로 읽게 한 설계(ADR-0005) 덕에 개편 중에도 최저가와 판매처 수는 빠지지 않았다.
- 사이트 개편은 한 번에 바뀌지 않고 요청마다 섞여 나올 수 있다. 한 번 받아 본 페이지만 보고 고치면 다른 쪽 형식을 놓친다. 몇 번 받아서 두 형식을 모두 확인했다.

## 남은 것

- 11-03 10:17부터 고친 코드가 배포되기 전까지 새 페이지를 받은 실행(465, 467, 469, 473, 477, 483~491 등)은 판매처 목록이 없다. 다시 받을 방법이 없다.
- 같은 기준으로 골라도 옛 목록과 다를 수 있다(동점 처리, 122688356처럼 원인을 모르는 차이). 판매처 순위나 1위 판매처를 쓰는 분석은 11-03 전후를 나눠 봐야 한다.
