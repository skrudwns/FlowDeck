# 기록 원칙

## 목적

개발하면서 실제로 겪은 문제와 상황, 그리고 무엇을 어떤 생각으로 설계하고 고쳤고 무엇을 배웠는지를 사실대로 남긴다.

글을 잘 쓰는 게 목적이 아니다. 나중에 이 기록만 보고 "왜 이렇게 만들었는지", "그때 무엇이 문제였고 어떻게 판단했는지"를 설명할 수 있으면 된다.

## 담아야 할 것

- 상황: 무엇을 하려고 했고 무엇이 일어났나.
- 판단과 근거: 무엇을 고려했고, 어떤 선택지가 있었고, 왜 그것을 골랐나. 근거가 약했으면 약했다고 쓴다.
- 결과: 그래서 어떻게 됐나. 예상과 달랐다면 무엇이 달랐나.
- 수정: 처음 설계나 판단에서 바꾼 것과 바꾼 이유.
- 배운 것: 새로 알게 된 사실이나 바뀐 생각. 다른 상황에도 적용할 수 있을 만큼 구체적으로.
  - 막연함: "동시성 제어가 중요하다는 걸 배웠다"
  - 구체적: "앱 시작 이벤트는 워커 프로세스마다 실행된다. 프로세스당 하나만 있어야 하는 것은 웹 서버 안에 두지 않는다"

## 진실성

- 실제로 일어난 일만 쓴다. 문제를 부풀리지 않고, 해결 과정을 실제보다 매끄럽게 쓰지 않는다.
- 확인한 것과 추정한 것을 구분한다. 추정이면 추정이라고 쓴다.
- 수치는 실제로 측정한 값만 쓴다.
- 틀렸던 판단도 남긴다. 무엇이 틀렸고, 그때 왜 그렇게 생각했는지.
- 아직 모르는 것, 임시로 막아 둔 것은 그렇다고 쓴다.
- 판단의 주인은 개발자다. Claude가 초안을 쓸 때 사용자의 판단 이유를 짐작해서 채우지 않는다. 사용자가 한 말을 쓰거나, 모르면 물어본다.

## 쓰는 방식

- 간결하게, 사실 위주로. 목록이나 표가 편하면 그렇게 쓴다.
- 문장 끝은 "~했다" 서술체나 명사형("~함", "~로 변경")으로 통일한다. "~했습니다" 같은 존댓말 보고서체는 쓰지 않는다.
- 에러 메시지, 로그, 명령어는 근거 자료이므로 원문 그대로 붙인다.
- 파일명, 함수명, 설정값, 수치처럼 이 프로젝트에만 있는 정보를 쓴다.
- 템플릿에서 해당 없는 섹션은 지운다.

## AI가 쓴 것처럼 보이는 표현 피하기

AI가 쓴 기록은 대체로 내용이 일반적이고, 표현이 매끄럽고, 형식이 지나치게 고르다. 아래 표현이 나오면 고친다.

### 내용

| 피할 것 | 예 | 대신 |
|---|---|---|
| 어느 프로젝트에나 붙일 수 있는 문장 | "안정성과 확장성을 고려하여 설계했다" | 무엇을 어떻게 고려했는지. 예: "작업이 늘어도 API 서버를 건드리지 않게 수집기를 별도 프로세스로 뺐다" |
| 교과서식 개념 설명 | "FastAPI는 Python 기반의 고성능 웹 프레임워크로..." | 빼거나, 이 프로젝트에서 그걸 고른 이유만 |
| 근거 없는 평가와 과장 | "완벽하게 해결했다", "성능이 크게 향상됐다" | 확인한 범위와 측정값. 예: "평균 응답 820ms → 140ms (같은 데이터 1,000건 기준)" |
| 막연한 교훈 | "~의 중요성을 깨달았다", "값진 경험이었다" | 구체적으로 알게 된 사실이나 다음에 다르게 할 행동. 없으면 쓰지 않는다 |
| 가능성만 늘어놓기 | "~할 수 있다", "~에 활용될 수 있다" | 실제로 한 것, 실제로 할 계획만 |
| 없던 고민 만들기 | 실제로 비교하지 않은 선택지를 비교한 것처럼 쓰기 | 실제로 검토한 것만. 바로 정했으면 바로 정했다고 쓴다 |

### 표현

| 피할 것 | 예 | 대신 |
|---|---|---|
| 예고, 정리 문장 | "~에 대해 살펴보겠다", "결론적으로", "요약하면" | 바로 내용을 쓴다 |
| "~를 통해 ~할 수 있었다" | "캐시를 도입함으로써 응답 속도를 개선할 수 있었다" | "캐시를 넣었다. 응답 820ms → 140ms" |
| 번역투 | "~하는 것이 중요하다", "~를 가능하게 한다", "~에 있어서" | 주어와 동사를 바로 쓴다 |
| 추상적인 꾸밈말 | 효율적인, 원활한, 강력한, 견고한, 체계적인, 다양한, 최적화된 | 무엇이 어떻게 나아졌는지 |
| "A가 아니라 B" 강조 공식 | "단순한 버그가 아니라 설계 문제였다" | "설계 문제였다" |
| 긴 대시(—)로 문장 잇기 | "원인은 하나였다 — 캐시" | 마침표나 쉼표로 끊는다 |

### 형식

| 피할 것 | 대신 |
|---|---|
| 이모지 제목, 굵은 글씨 남발 | 제목은 평범하게. 굵은 글씨는 꼭 필요할 때만 |
| 항상 세 개씩 맞춘 목록 | 실제 개수대로. 하나면 하나 |
| 모든 항목의 길이와 문형을 똑같이 맞춤 | 중요한 건 길게, 사소한 건 한 줄로 |
| 짧은 내용에 소제목을 여러 개 | 내용이 짧으면 소제목 없이 |
| 맨 끝에 앞 내용을 되풀이하는 요약 | 요약이 필요하면 맨 위 한 줄 |

### 점검 질문

기록을 마무리하기 전에 확인한다.

- 이 문장에서 프로젝트 이름만 바꾸면 다른 프로젝트 기록이 되는가? 그렇다면 구체적으로 고치거나 지운다.
- 평가하는 말(개선됐다, 안정적이다)마다 근거가 있는가?
- 실제로 하지 않은 고민이나 검토가 들어가 있지 않은가?
- 소리 내어 읽었을 때 내가 평소에 쓰지 않는 표현이 있는가?

## 예시

가상의 상황이다.

내용이 비어 있는 기록:

> 스케줄러 중복 실행 문제가 발생하여 구조를 개선했다. 이를 통해 안정성을 높였고 동시성 제어의 중요성을 배웠다.

남겨야 하는 기록:

> - 문제: 같은 상품 가격이 같은 시각에 두 건씩 저장됨. 두 건의 `run_id`가 서로 다름.
> - 확인: 수집기 재시도를 먼저 의심. 로그에 재시도 기록 없음. 수집기가 두 번 돈 게 아니라 작업이 두 번 등록된 것으로 판단.
> - 원인: 스케줄러를 API 앱 시작 이벤트에서 띄우고 있었음. 운영은 `--workers 2`라 스케줄러도 두 개. 로컬은 워커 하나라 재현 안 됨.
> - 선택지: (a) 락으로 중복 실행 방지, (b) 스케줄러를 별도 프로세스로 분리. (a)는 증상만 막고 스케줄러가 여러 개 뜨는 구조는 그대로라 (b)를 선택.
> - 배운 것: 앱 시작 이벤트는 워커마다 실행된다. 프로세스당 하나만 있어야 하는 것은 웹 서버 안에 두지 않는다.

## 커밋 전 확인

초안을 Claude가 썼더라도 커밋 전에 사용자가 읽고 확인한다.

- 설명할 수 없는 내용이 없는지
- 판단 이유가 실제 내 생각과 맞는지
