## 판단과 근거

### Neon 유지

- Supabase도 되는지 물어봤다. 둘 다 Postgres라 코드는 같다.
- Supabase 무료 프로젝트는 7일 동안 활동이 적으면 프로젝트가 일시 정지되고 직접 복구해야 한다. 직접 DB 접속이 "활동"에 들어가는지는 문서에서 확인하지 못했다. 몇 주 연속 수집이 목적이라 이 위험이 없는 Neon을 유지했다.

### 다나와

- 11번가 API는 호출할 IP를 미리 등록해야 해서, 실행마다 IP가 바뀌는 GitHub Actions(ADR-0003)와 맞지 않았다. 등록도 실패했다.
- 다나와는 robots.txt가 상품 페이지를 막지 않고, 가격비교 사이트라 상품 하나에 여러 판매처 가격이 같이 나온다.
- 법률 검토를 받은 건 아니다. 야놀자-여기어때 판례(형사 무죄, 민사 약 10억 원 배상)를 보고, 위험을 줄이는 쪽으로 원칙을 정했다. 소수 상품, 1시간 1회, 가격·판매처·시각만 저장, 차단되면 멈춤, 원본 데이터 비공개.

### 수집 범위

- 판매처 전체 목록은 `/info/ajax/getAllPriceCompareMallList.ajax.php`로 따로 불러오는데, robots.txt가 `/info/ajax/`를 막는다. 그래서 처음 받는 HTML에 있는 것만 쓴다. 최저가·판매처 수는 JSON-LD, 상위 판매처는 화면 HTML.
- JSON-LD는 검색엔진용 데이터라 화면 개편에 덜 흔들릴 것으로 봤다. 상위 판매처 파싱이 실패해도 최저가는 저장하도록 둘을 분리했다.

### 구현에서 정한 것

- User-Agent: 브라우저로 위장하지 않고 `FlowDeckCollector/0.1 (+https://github.com/skrudwns/FlowDeck)`. 이 UA로 상품 페이지를 요청해 200과 정상 HTML이 오는 걸 curl로 확인한 뒤 정했다.
- robots.txt는 실행마다 한 번 받아서 확인한다. 파이썬 `urllib.robotparser`는 경로 와일드카드를 지원하지 않는데, prod.danawa.com 규칙은 지금 단순 접두어뿐이라 그대로 썼다.
- 테스트용 HTML은 다나와 원본을 저장소에 넣지 않으려고 구조만 본떠 가짜 값으로 만들었다 (수집 원칙 6).
- 수집 실행 테스트는 SQLite가 아니라 로컬 Postgres의 `flowdeck_test` DB에서 돌린다. 운영과 같은 DB에서 확인하려고 Claude가 정했다. 대신 테스트에 Docker가 필요하다. DB가 없으면 건너뛴다.
- HTML 파싱 라이브러리 selectolax는 Claude가 골랐고 다른 것과 비교하지는 않았다.
- 수집 대상은 파일로 관리한다. 무엇을 언제 넣고 뺐는지 git에 남는다. 파일에서 빠진 상품은 지우지 않고 비활성화만 한다.

### GitHub Actions

- 수집 워크플로는 매시 17분. GitHub 문서에 매시 정각이 부하가 높은 시간이고 부하가 심하면 대기 중인 작업이 빠질 수 있다고 되어 있어서 정각을 피했다.
- 실행마다 `alembic upgrade head` → `products sync` → `collect` 순서로 돈다. 스키마와 대상 목록이 main에 합쳐지면 다음 실행에 Neon에 자동으로 반영된다. 대신 잘못된 마이그레이션도 바로 운영 DB에 들어간다. 지금은 혼자 쓰는 DB라 이 편이 낫다고 봤다.
- 같은 시간에 두 번 돌지 않게 `concurrency`로 묶었다.
- 수집이 전부 실패하면 `flowdeck collect`가 종료 코드 1을 돌려서 Actions에 실패로 보인다. 일부만 실패하면 성공으로 보이고, 자세한 건 DB의 실행 기록에 남는다.
- CI는 Postgres 17 서비스 컨테이너를 띄워 DB 테스트까지 돌린다. 로컬에서는 DB가 없으면 DB 테스트를 건너뛰는데, CI에서 그러면 DB 테스트가 하나도 안 돈 채 통과로 보인다. 그래서 CI에서는 `REQUIRE_TEST_DB`로 연결 실패를 에러로 만든다.
- 사용한 액션 버전(`actions/checkout@v7`, `astral-sh/setup-uv@v10`)은 GitHub API로 최신 릴리스를 확인하고 정했다.

### 수집 주기 실행 방식

- 예약 실행이 안 도는 상황에서 선택지는 외부 cron으로 workflow_dispatch 호출, 저장소를 공개로 바꿔 예약 재시도, 노트북 cron, 클라우드 서버였다.
- 외부 cron으로 정했다(사용자 결정). 수동 실행은 오늘 여러 번 동작을 확인했고, 예약 실행은 원인을 모른 채 안 도는 상태였다. 공개 전환은 코드와 커밋 이력이 공개되고, 공개해서 돈다는 보장도 없었다.
- 토큰은 이 저장소, Actions 쓰기 권한만 준 fine-grained 토큰으로 했다. 만료일은 2027-01-22.
- 워크플로에서 schedule은 뺐다. 예약 실행이 나중에 다시 돌기 시작하면 한 시간에 두 번 수집하게 되기 때문.
- 1시간을 기다리지 않고 예약이 도는지 보려고 5분마다 echo만 하는 임시 워크플로를 넣었다가 뺐다. 수집 워크플로 주기를 줄이면 다나와 요청이 늘어서 따로 만들었다.

### 수집 감시 (#10)

- 수집이 아예 안 돌면 수집기 코드도 안 돌아서, 안 돌았다는 건 바깥에서 봐야 한다. 실행마다 Healthchecks.io에 신호를 보내고, 끊기면 Healthchecks.io가 알리는 방식으로 했다 (ADR-0007, 사용자 결정).
- GitHub 실패 알림과 cron-job.org 실패 알림만으로는 cron-job.org가 통째로 멈추는 경우를 못 잡는다. cron-job.org로 감시용 워크플로를 따로 돌리면 감시와 수집이 같이 멈춘다.
- `/fail` 기준: 실행 실패, 차단, 요청·파싱 실패 3개 이상, 판매처 목록 파싱 실패 3개 이상. 3이라는 숫자는 근거 없이 정한 처음 값이다. 1~2개는 다나와 쪽 일시 오류일 수 있어서 본문에만 남긴다.
- 판매처 목록 파싱 실패를 따로 센 이유: 최저가는 JSON-LD에서 읽어서 화면 HTML이 바뀌어도 실행은 성공으로 나온다. 그러면 조용히 판매처 데이터만 비게 된다.
- 문제가 있으면 `flowdeck collect`가 종료 코드 1로 끝나게 바꿨다. 전에는 전부 실패일 때만 1이라 일부 실패는 Actions 화면에서 초록으로 보였다.
- 신호 주소를 알면 누구나 가짜 성공 신호를 보낼 수 있어서 Secret으로 두고 로그에도 남기지 않는다.
- 확인한 것: 수동 실행에서 신호 전송 성공, Healthchecks.io에 요약이 본문으로 들어옴(사용자 확인), 테스트 알림 메일 수신(사용자 확인). 신호가 끊겼을 때 실제로 알림이 오는지는 수집을 일부러 멈춰야 확인할 수 있어서, 테스트 알림으로 대신했다.

### 포털 API (#11)

- FastAPI 엔드포인트를 동기(`def`)로 만들고 수집기의 SQLAlchemy 세션을 그대로 쓴다. async로 가면 DB 접근 코드가 두 벌이 된다. 사용자가 몇 명뿐이라 비동기로 얻을 게 없다고 봤다. Claude가 정했다 (ADR-0008).
- 상품 목록에는 상품마다 가장 최근 수집 결과를 붙였다. 상품 20개를 한 번에 가져오려고 Postgres `DISTINCT ON`을 썼다.
- 가격 이력에 실패한 수집도 넣었다. 가격 없이 상태만 보이게 해서, 화면에서 수집이 빈 구간이 보이게 하려는 것.
- 응답 형식은 pydantic 스키마로 따로 정의했다. 테이블을 바꿔도 API 응답이 바로 바뀌지 않게.
- 로컬 DB로 서버를 띄워 7개 경로를 실제로 호출해 봤다. `/docs`도 열린다.

### 포털 웹 (#14)

- Next.js 16, Tailwind, 컴포넌트 라이브러리 없이. 서버 컴포넌트에서 API를 불러서 CORS 설정과 API 주소 노출이 없다. Claude가 정했다 (ADR-0009).
- API 타입은 FastAPI OpenAPI 문서에서 만든다. 서버를 띄우지 않고 뽑으려고 `flowdeck openapi` 명령을 만들었다. CI가 타입을 다시 만들어 커밋된 것과 다르면 실패한다. 백엔드 응답을 바꾸고 타입을 안 만들면 바로 드러난다.
- 작업 목록 화면에 "다음 실행 시각"이 필요해서 `/jobs` API를 추가했다. 작업 정의를 코드에 두니 주기가 코드와 cron-job.org 두 군데에 있게 됐다. #16에서 합친다.
- 흐름 화면의 단계 상태는 마지막 실행 결과에서 계산한다. 알림 단계 결과는 Healthchecks.io에만 있어서 "알 수 없음"으로 둔다.
- create-next-app이 만든 `AGENTS.md`에 "이 버전의 Next.js는 알던 것과 다르니 `node_modules/next/dist/docs/`를 먼저 읽으라"고 되어 있었다. 읽어 보니 실제로 달랐다.
  - `cacheComponents`가 기본으로 켜져 있다. 요청마다 가져오는 데이터와 `params`·`searchParams`는 `<Suspense>` 안에서 읽어야 한다. ADR-0009에 적은 `cache: "no-store"` 계획을 고쳤다.
  - 오류 화면(`error.tsx`)이 받는 다시 시도 함수 이름이 `reset`이 아니라 `retry`다.
  - 덕분에 빌드할 때 API 서버가 없어도 된다. 데이터 화면은 정적 틀만 만들고 데이터는 요청 때 채운다(Partial Prerender).
- Recharts 3은 `ResponsiveContainer` 대신 차트에 `responsive` 속성을 줄 수 있다. 타입 정의 주석에서 확인했다.
- 가격 차트는 계단형으로 그렸다. 가격은 다음 수집 전까지 유지된 값이라서. 실패한 수집은 가격이 비어 선이 끊긴다.
- 로컬 DB와 API를 띄워 화면 5개를 모두 브라우저로 확인했다. 검색, 404, API가 꺼졌을 때 오류 화면까지.

### 수집 대상 고르기

- SSD 2TB, DDR5 32GB, RTX 5070, 무선이어폰, 로봇청소기, 모니터 27인치를 다나와 검색에 넣고 분야별 인기 상위 6개, 총 36개를 후보로 뽑았다. 검색 페이지 robots.txt의 `Crawl-delay: 10`에 맞춰 검색은 10초 간격으로 요청했다.
- 후보마다 상품 페이지에서 판매처 수를 확인하고, 판매처가 많은 순으로 분야별 2~4개, 총 20개를 골랐다. 판매처가 많을수록 가격이 자주 움직일 것으로 봤다. 실제로 그런지는 데이터를 쌓아 봐야 안다.

## 문제

- 네이버 쇼핑 검색 API 종료. 등록 화면의 사용 API 목록에 "검색"이 없었다. 2026-07-31에 종료됐고 대체 API는 없다. 경위는 ADR-0002 돌아보기.
- 11번가 서비스 등록 "시스템 오류". 원인은 모른다.
- 원격에 이미 올라간 커밋을 amend해서 로컬과 원격 브랜치가 갈라졌다. TS-0001.
- selectolax 1.0에서 기존 엔진이 빠져 import부터 실패했다.

  ```
  ImportError: Modest backend is deprecated since selectolax 1.0. ... Please use lexbor backend instead: `from selectolax.lexbor import LexborHTMLParser`.
  ```

  에러 메시지가 안내한 대로 lexbor 엔진으로 바꿨다. 테스트 13개가 통과했고, 저장해 둔 실제 페이지 2개로도 확인했다.
- CI가 시작하자마자 실패했다. `astral-sh/setup-uv@v10` 태그가 없었다. setup-uv는 v8부터 major 태그를 만들지 않는다. 전체 버전 태그로 고정해서 해결. TS-0002.
- 수집 워크플로 예약 실행이 돌지 않았다. 수동 실행은 같은 파일로 성공했고, main 반영, 비활성화 여부, 장애 공지는 확인했다. GitHub 직원 답변대로 main에 커밋을 넣어 재동기화해 봤지만 효과가 없었고, echo만 하는 5분 주기 워크플로도 안 돌았다. GitHub은 건너뛴 예약의 이유를 남기지 않아서 원인은 끝내 모른다. 외부 cron으로 우회해서 해결. TS-0003.
- SQLAlchemy 2.1에서 `select().distinct(컬럼)`으로 DISTINCT ON을 만드는 방식이 deprecated였다.

  ```
  SADeprecationWarning: Passing expression to ``distinct`` to generate a DISTINCT ON clause is deprecated. Use instead the ``postgresql.distinct_on`` function as an extension.
  ```

  `select().ext(distinct_on(컬럼))`으로 바꿨다. 라이브러리 docstring에서 새 방식을 확인했다.
- Starlette 1.9의 TestClient가 `httpx` 대신 `httpx2`를 쓰라고 경고한다. `httpx2`가 httpx 작성자(Tom Christie)의 pydantic 저장소 패키지이고 Starlette가 선택 의존성으로 명시한 것까지 확인했지만, 새 외부 패키지라 설치는 권한 제한으로 막혔다. 테스트는 통과하고 경고만 남아 있었다. 사용자가 허락해서 개발 의존성으로 설치했고, 경고를 에러로 바꿔도 테스트 65개가 통과하는 것을 확인했다.
- 서버를 셸에서 `( uv run uvicorn ... & )`로 띄웠더니 `Failed to spawn: uvicorn`으로 실패했다. uvicorn은 `.venv`에 설치돼 있었다. 백그라운드 서브셸에서 uv가 프로젝트를 다르게 잡은 것으로 추정하고, `.venv/bin/uvicorn`을 직접 실행해서 띄웠다. 원인은 확인하지 않았다.
- Recharts가 peer 의존성으로 요구하는 `react-is`가 다른 패키지가 끌어온 16.13.1로 잡혀 있었다. Recharts README가 React와 버전을 맞추라고 해서 19.3.0을 설치했다.
- 데스크톱 앱 미리보기로 API·웹 서버를 띄울 때 두 번 막혔다.
  - 상대 경로(`cd backend`)가 `getcwd: cannot access parent directories: Operation not permitted`로 실패했다. 미리보기 실행기가 저장소 밖에서 시작하는 것으로 보고 절대 경로로 바꿨다.
  - API를 8000으로 설정했는데 미리보기 도구가 8001로 옮겨 띄워서, 웹이 `ECONNREFUSED 127.0.0.1:8000`으로 API를 못 찾았다. 포트를 8010으로 고정하고 자동 변경을 껐다.
- API를 끄고 오류 화면을 확인할 때 처음엔 "불러오는 중"에서 멈춘 것처럼 보였다. 서버가 보낸 HTML 스트림에 오류가 실려 있는 걸 확인하고 다시 기다려 보니 오류 화면이 떴다. 개발 모드 스트리밍이 끝나기 전에 너무 일찍 본 것이었다.
- 처음에 상위 판매처가 "최대 5곳"이라고 설계에 적었는데, 후보 36개를 보니 31개가 10곳이었다. 문서와 주석만 고쳤다. ADR-0005 돌아보기.

## 배운 것

- 외부 API에 기대는 결정은 공식 문서에서 현재 제공 여부를 확인하고, 키를 받아 한 번 호출해 본 뒤에 채택한다. 이번에 커뮤니티 예시만 보고 채택했다가 이미 종료된 API였다.
- amend나 rebase 전에 `git fetch`로 원격에 이미 있는지 확인한다. 데스크톱 앱에서 커밋하면 push까지 같이 될 수 있다.
- 표본 두 개로 "최대 몇 개" 같은 상한을 적지 않는다.
- 액션 버전은 릴리스 이름이 아니라 실제 태그가 있는지 확인하고 적는다.
- GitHub Actions 예약 실행은 문서에 "늦어지거나 빠질 수 있다"고 적힌 기능이다. 실행 위치를 고를 때 그 문장을 읽었지만 몇 시간씩 안 돌 가능성까지는 따지지 않았다.
- robots.txt는 같은 회사라도 서브도메인마다 다르다. prod.danawa.com에는 Crawl-delay가 없고 search.danawa.com에는 10초가 있었다.
