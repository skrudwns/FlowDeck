## 판단과 근거

### 프로젝트 목적

- 외주 포트폴리오. 외주 클라이언트가 실제로 필요로 할 만한 것을 만든다.
- 개발 과정과 그 과정에서 겪는 문제, 설계·수정 판단을 기록으로 남긴다.

### 주제

방향은 웹/앱 기반의 자동화, 모니터링, 데이터 분석. 후보는 두 개였다.

1. 자동화 작업 관리 포털. 정해진 페이지를 주기적으로 수집해 변동을 기록하고, 조건에 맞으면 알림을 보내고, 클라이언트가 포털에서 관리한다. 예시 시나리오는 온라인 셀러를 위한 경쟁사 가격 모니터링.
2. 주기적으로 데이터를 수집하고, 분석 로직으로 새로운 정보를 만들어 낸다.

결정: 둘을 합친다. 포털을 수집 → 가공 → 저장 → 분석 → 알림 단계로 일반화하고, 가격 모니터링을 첫 시나리오로 올린다. 2번은 이 중 분석 단계가 된다.

검토한 내용:

- 1번만 하면 일반적인 "크롤러 + 관리자 페이지"와 차별점이 약하다.
- 2번만 하면 클라이언트가 직접 쓰는 형태가 드러나지 않는다.
- 단계를 일반화해 두면 다른 업무에도 같은 구조를 쓸 수 있다는 걸 보여줄 수 있다. 후반에 두 번째 시나리오를 붙여 확인할 계획.

포털 기능: 작업 목록(다음 실행 시각, 마지막 결과), 실행 이력과 로그, 수집 데이터 조회(표, 차트, 필터, 엑셀/CSV), 수동 실행·주기 변경·대상 관리, 알림 설정, 단계 흐름 시각화, 분석 탭.

분석 후보: 평소 대비 급락 감지, 요일/시간대별 할인 패턴, 경쟁사 중 내 가격 순위, 품절·재입고 감지, 주간 리포트. 실제로 무엇을 만들지는 데이터를 모아 본 뒤 정한다.

### 미리 확인한 제약

- 실제 쇼핑몰만 대상으로 하면 사이트 구조가 바뀔 때 데모가 깨진다. 데모용 연습 쇼핑몰을 만들고, 실데이터는 공식 API로 보충하는 방안을 검토 중.
- 카카오톡 알림톡은 비즈니스 채널과 대행사가 필요하다. 개인 프로젝트에서는 "나에게 보내기" API 수준까지 가능.
- 분석에는 몇 주치 데이터가 필요하다. 실데이터 수집을 일찍 시작해야 한다.

### 작업 규칙

- 커밋을 문제, 기능, 수정, 리팩토링 단위로 잘게 나눈다. 개발 과정을 단위별로 따라갈 수 있게 하기 위해서.
- 커밋 제목 형식은 `타입(범위): 제목`. commit-msg 훅으로 검사한다. 정상 메시지 7개, 잘못된 메시지 6개로 테스트했고 모두 의도대로 통과/차단됐다.
- 기록 종류: 개발 일지, 트러블슈팅, 기술 결정(ADR), 분석 노트.
- 커밋에 `Co-Authored-By:` 트레일러는 넣지 않기로 했다.

### 기술 스택

- 내세우고 싶은 스택이 따로 없어서 기준만 정했다. 웹 기반이되 앱에서도 연동할 수 있을 것, 수집과 분석을 제대로 가져갈 수 있을 것.
- Claude가 제안한 Python(FastAPI) + Next.js + PostgreSQL 구성을 채택했다. 앱 연동은 API를 먼저 설계하고 웹은 PWA로 만드는 방식.
- 작업 큐, 스케줄러, 배포 환경은 필요해질 때 정한다. 자세한 내용은 [ADR-0001](../adr/0001-tech-stack.md).

## 수정

- 기록 지침을 처음에는 "문체 가이드"로 만들었다. 시간 흐름 묘사, 문장 길이 같은 글쓰기 방식에 초점을 둔 내용이었다.
- 기록의 목적은 글을 생생하게 쓰는 게 아니라, 실제 겪은 문제와 설계·수정·배움의 사고 과정을 사실대로 남기는 것이다. 그래서 "기록 원칙"(`record-principles.md`)으로 다시 썼다. 판단 근거, 검토한 선택지, 수정 이유, 배운 것을 담는 데 집중하고, 템플릿에도 "판단과 근거", "수정", "배운 것" 항목을 넣었다.
