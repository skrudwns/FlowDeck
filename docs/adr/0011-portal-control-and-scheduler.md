# ADR-0011: 포털 직접 제어와 작업 스케줄러

- 날짜: 2026-10-25
- 상태: 채택
- 관련: #16, ADR-0001, ADR-0003, ADR-0004, ADR-0006, ADR-0007, ADR-0009, ADR-0010

## 상황

- 포털에서 수동 실행, 주기 변경, 수집 대상 추가·삭제를 하게 만든다 (#16).
- 지금 주기는 cron-job.org(매시 17분)에, 다나와 수집 대상은 파일(`backend/targets/danawa.txt`)에 묶여 있다. 수집 워크플로가 실행마다 파일을 DB에 맞추기 때문에, 포털에서 DB를 바꿔도 다음 실행에 파일 내용으로 되돌아간다.
- ADR-0001은 작업 큐와 스케줄러를 "수동 실행과 주기 변경을 실제로 만들 때" 정하기로 미뤘다. ADR-0003은 그때 수집 실행 위치도 다시 보기로 했다.
- 포털 API와 웹은 아직 로컬에서만 띄운다. 배포와 인증은 정하지 않았다 (ADR-0009).
- 비용은 들이지 않는다는 조건은 그대로다 (ADR-0003).

## 선택지: 스케줄러와 실행 위치

### A. 수집은 GitHub Actions에 두고, 주기를 DB로 옮긴다

cron-job.org는 지금처럼 매시 17분에 워크플로를 호출한다. 워크플로가 먼저 DB의 주기와 실행 요청을 보고, 지금 돌 작업만 실행한다.

- 좋은 점: 비용, 서버, cron-job.org 설정 변경이 없다. 지금 돌고 있는 수집 경로를 그대로 쓴다.
- 걸리는 점: 호출이 1시간에 한 번이라 주기는 시간 단위로만 바꿀 수 있다. 몇 분에 돌지는 cron-job.org가 정한다.

### B. 상시 서버에서 API와 스케줄러(작업 큐)를 돌린다

- 좋은 점: 주기를 분 단위로 바꿀 수 있고, 수동 실행이 바로 같은 서버에서 돈다.
- 걸리는 점: 상시 서버가 필요하다. 월 5달러 안팎이거나 카드 등록이 필요한 무료 등급이다 (ADR-0003). 배포도 이번에 같이 정해야 한다.

### 결정

A. 사용자가 골랐다. ADR-0003의 "포털이 생기면 수집을 스케줄러 쪽으로 옮길지 다시 정한다"는 옮기지 않는 것으로 정리한다.

## 선택지: 수동 실행을 언제 돌리나

- 바로: 포털 API가 GitHub API로 워크플로를 실행한다(workflow_dispatch). Actions 쓰기 권한 토큰이 API 쪽에 있어야 한다.
- 다음 정기 호출 때: 요청만 DB에 남기고 다음 매시 17분에 실행한다. 토큰은 필요 없지만 최대 1시간을 기다린다.

바로 실행하는 쪽을 사용자가 골랐다. 토큰이 없거나 GitHub 호출이 실패하면 요청은 DB에 남아 있다가 다음 정기 호출 때 실행된다. 그래서 두 방식은 같은 실행 요청 테이블을 쓴다.

아래는 사용자가 따로 고르지 않았고 Claude가 정했다.

## 작업 큐

- Postgres 테이블 `run_requests`가 작업 큐다. 별도 큐 서비스(Redis 등)는 두지 않는다. 요청은 많아야 하루 몇 건이고, 실행하는 쪽(Actions)이 상시 떠 있는 워커가 아니라 큐 서비스에 붙어 있을 수가 없다.
- 요청 상태는 `pending`(대기)과 `done`(실행에 연결됨) 둘뿐이다. 수집 실행이 끝나면 그 작업의 대기 요청 중 실행 시작 전에 들어온 것을 그 실행에 연결한다. 실행이 예상 못 한 오류로 끝나도 연결한다. 연결하지 않으면 다음 호출마다 다시 실행된다.
- GitHub 호출 결과(보낸 시각, Actions 실행 주소, 실패 원인)는 요청 행에 남긴다.
- 작업마다 대기 요청은 하나만 둔다. 이미 있으면 새 요청을 거절한다.

## 주기

- 작업별 주기는 `job_schedules` 테이블에 둔다: 몇 시간마다(`interval_hours`), 켜짐 여부(`enabled`). 작업 정의(이름, 수집 대상, 설명)는 지금처럼 코드에 둔다. 수집 대상마다 수집 코드가 따로 있어서, 코드 없이 작업만 DB에 추가할 수는 없다.
- 고를 수 있는 주기: 1, 2, 3, 4, 6, 8, 12, 24시간. 24의 약수만 둬서 실행 시각이 날마다 같게 한다. 실행 시각은 한국 시간 0시부터 주기마다, 매번 17분이다 (6시간이면 0:17, 6:17, 12:17, 18:17).
- 끄면 정기 실행만 멈춘다. 수동 실행은 된다.
- ADR-0009에서 주기가 코드와 cron-job.org 두 군데에 있던 문제는, 주기는 DB에, cron-job.org는 "매시 17분에 확인하라"는 호출만 하게 바뀌면서 정리된다.

## 실행 판단 (워크플로 앞 단계)

워크플로가 호출되면 먼저 `flowdeck plan`이 작업마다 돌지 말지 정한다. 호출한 쪽(cron-job.org, 포털, GitHub 화면)과 상관없이 매번 같은 규칙으로 본다.

1. 그 작업의 대기 요청이 있으면 수동 실행.
2. 켜져 있고, 가장 최근 실행 시각(위 규칙의 HH:17)이 지났고, 그 시각 이후에 시작한 실행이 없으면 정기 실행. 정기 호출을 하나 놓치면 다음 호출 때 따라잡는다.
3. GitHub 화면에서 직접 실행(`trigger=manual`)했으면 모든 작업을 수동 실행. 점검용이다.
4. 다나와는 1~3과 상관없이, 같은 시(한국 시간 HH:00~HH:59)에 이미 시작한 실행이 있으면 돌지 않는다.

매번 같은 규칙으로 보는 이유: 워크플로는 `concurrency`로 묶여 있어서 대기열에 하나만 남는다. 포털 호출과 정기 호출이 겹치면 하나는 취소된다. 어느 쪽이 남든 둘 다 처리하게 하려는 것이다.

GitHub 문서: "By default, any existing `pending` job or workflow in the same concurrency group will be canceled". 같은 문서에 `queue: max`로 최대 100개까지 대기시키는 설정이 있다는 건 이 ADR을 쓴 뒤 다시 읽다가 알았다. 대기열을 늘리면 겹친 호출만큼 워크플로가 연달아 돈다. 위 규칙으로 취소돼도 빠지는 작업이 없어서 기본 동작을 그대로 둔다.

### 다나와 "1시간에 한 번" 해석

ADR-0004 수집 원칙 2는 "1시간에 한 번"이다. 수동 실행이 생기면서 이걸 코드로 정해야 했다. 시계 기준으로 한 시(HH:00~HH:59)에 최대 한 번으로 정했다. 하루 최대 24번은 지켜지지만, 3:59 수동 실행과 4:17 정기 실행처럼 간격이 60분보다 짧을 수는 있다.

60분 이동 구간으로 막으면 정기 실행 시작 시각이 몇십 초만 흔들려도(3:17:40 다음 4:17:05) 정기 실행이 빠진다. 허용 오차를 따로 두는 것보다 시 단위가 단순하고 테스트하기 쉬워서 이렇게 했다. 포털은 이 규칙에 걸리는 수동 실행 요청을 받을 때 바로 거절하고 언제부터 되는지 알려준다. 연습 쇼핑몰은 우리 쇼핑몰이라 이 제한이 없다.

## 감시

- 주기를 6시간으로 바꾸면 Healthchecks.io(매시 신호 기대, ADR-0007)는 5시간 동안 "신호 없음"으로 알린다.
- 그래서 실행 판단 단계가 이번 호출에서 돌지 않는 작업에도 그 작업의 체크로 성공 신호를 보낸다. 본문에 "주기가 아니라 건너뜀", "꺼져 있음" 같은 이유를 남긴다.
- 체크의 뜻이 "매시 수집이 돌았다"에서 "매시 스케줄러가 돌았고, 수집이 돌았다면 문제없었다"로 바뀐다. cron-job.org나 Actions가 멈추는 것은 여전히 잡힌다. 꺼 둔 작업이 오래 안 돈다는 건 잡지 않는다. 사람이 끈 것이기 때문이다.

## 수집 대상

- 다나와 수집 대상의 기준을 파일에서 DB로 옮긴다. 워크플로의 `products sync` 단계를 빼고 `targets/danawa.txt`는 지운다. 파일 내용은 git 이력에 남는다. Neon의 상품 상태는 마지막 sync로 파일과 같은 상태다.
- 파일을 두면 무엇을 언제 넣고 뺐는지가 git 이력에 남았다. 이것을 잃지 않으려고 `audit_log` 테이블에 대상 추가·중지·재개, 주기 변경, 수동 실행 요청을 남긴다. 누가 했는지는 인증이 없어서 경로(포털, CLI)로만 남긴다.
- 포털에서 다나와 상품은 pcode로 추가하고, 중지·재개한다. 지우지는 않는다(ADR-0005, 가격 기록 유지).
- 활성 다나와 상품은 30개까지만 받는다. ADR-0004 수집 원칙 1(20개 안팎)이 포털 입력으로 깨지지 않게 하려는 상한이다. 30이라는 숫자는 20에 여유를 둔 값이고 다른 근거는 없다.
- 연습 쇼핑몰 상품은 쇼핑몰 목록으로 정해져서(ADR-0010) 포털에서 추가·중지하지 않는다.

## API와 웹

| 요청 | 내용 |
|---|---|
| `POST /jobs/{id}/run-requests` | 수동 실행 요청. 대기 요청이 있거나 다나와 시간 제한에 걸리면 409 |
| `PATCH /jobs/{id}` | 주기, 켜짐 변경 |
| `POST /products` | 다나와 상품 추가 (이미 있으면 다시 활성화) |
| `PATCH /products/{id}` | 중지, 재개 |
| `GET /audit-log` | 변경 이력 |

- 웹은 Server Action으로 API를 부르고 `refresh()`로 화면을 다시 그린다. 웹이 API를 서버에서만 부르는 구조(ADR-0009)를 그대로 쓴다.
- 인증은 없다. 포털을 로컬에서만 띄우기 때문이다. 쓰기 경로가 생겼으므로 배포 전에 인증을 반드시 넣는다.

## 감수하는 것

- 주기는 시간 단위로만 바꾼다. 분 단위로 하려면 cron-job.org 호출을 더 자주 하거나 상시 서버(B)로 가야 한다.
- 포털에서 바로 실행하려면 GitHub 토큰이 API 서버에 있어야 한다. 토큰은 이 저장소의 Actions 쓰기 권한만 가진 것으로 따로 만든다. cron-job.org에 넣은 토큰과 같이 쓰지 않는다. 하나가 새면 둘 다 바꿔야 하기 때문이다.
- 수동 실행도 Actions 실행 준비 시간(지금 1분 안팎) 뒤에 시작한다.
- 다나와는 시 단위 규칙 때문에, 매시 주기일 때 그 시의 정기 실행이 이미 돌았으면 수동 실행을 할 수 없다.
- 감시 신호의 뜻이 넓어졌다 (위 감시).
