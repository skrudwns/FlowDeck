# ADR-0012: 수집 워크플로를 한 job으로

- 날짜: 2026-10-25
- 상태: 채택
- 관련: #27, ADR-0003, ADR-0010, ADR-0011

## 상황

- 저장소는 비공개(Private)다. 2026-10-25 저장소 페이지에서 확인했다. ADR-0010에 "공개 저장소라 무료 한도 걱정은 없다"고 쓴 건 틀렸다.
- 계정은 GitHub Pro이고 Actions가 월 3,000분 포함이다 (결제 화면의 포함 사용량). 10월 사용량은 $1.05어치로 포함 사용량 안이다.
- GitHub 문서: "If your account does not have a valid payment method on file, usage is blocked once you use up your quota." 한도를 넘으면 수집이 멈춘다.
- #15, #16을 거치며 수집 워크플로가 매시 job 3개가 됐다. job마다 체크아웃, uv 설치, 의존성 설치를 따로 한다.

Actions 화면의 job별 실행 시간:

| 실행 | 구성 | 시간 |
|---|---|---|
| #13 (#15 전) | collect | 1분 44초 |
| #24 (#15 후) | migrate 19초, danawa 1분 39초, mockshop 53초 | 합계 2분 51초 |
| #28 (#16 후, 14:17 정기) | plan 21초, danawa 1분 37초, mockshop 53초 | 합계 2분 51초 |

- 매시 2분 51초면 한 달(31일) 2,120분 안팎이다.
- job마다 분 단위로 올려 센다면 1+2+1 = 4분, 한 달 2,976분이다. 올려 세는지는 GitHub 요금 문서에서 확인하지 못했다 ("Minutes are calculated based on the total processing time used by each runner type during the month"까지만 나온다).
- 여기에 push와 PR마다 도는 CI(backend, mock-shop, web 3개 job)가 더해진다.

## 선택지

### A. 수집 워크플로를 한 job으로 합친다

- 좋은 점: 준비 단계가 세 번에서 한 번으로 준다. 비용과 계정 변경이 없다.
- 걸리는 점: 다나와와 연습 쇼핑몰이 나란히가 아니라 차례로 돈다. 다나와가 실패하면 연습 쇼핑몰이 성공해도 job 전체가 실패로 보인다.

### B. 저장소를 공개로 바꾼다

- 좋은 점: 공개 저장소는 Actions가 무료다 (ADR-0003 무료 한도).
- 걸리는 점: 공개 전에 기록과 코드에 공개하면 안 되는 내용이 없는지 점검해야 한다. 포트폴리오라 언젠가는 공개하지만 지금 할 준비는 안 돼 있다.

### C. 연습 쇼핑몰 주기를 늘린다

- 좋은 점: 포털에서 바로 바꿀 수 있다.
- 걸리는 점: plan 단계는 매시 그대로 돌아서 준비 단계 중복은 남는다. 데모 데이터가 줄어든다.

## 결정

A. 사용자가 골랐다.

- plan, 다나와 수집, 연습 쇼핑몰 띄우기와 수집을 한 job의 단계로 둔다.
- 연습 쇼핑몰 단계는 `always()`로 둬서 다나와 수집이 실패해도 돈다. 나란히 돌 때 "한쪽이 실패해도 다른 쪽은 돈다"(ADR-0010)를 유지하려는 것이다.
- 실제로 줄어든 시간은 병합 후 정기 실행에서 재서 아래 돌아보기에 적는다.

## 감수하는 것

- 연습 쇼핑몰 수집이 다나와 수집이 끝난 뒤 시작한다. 지금까지 매시 18분 안팎이던 연습 쇼핑몰 수집 시각이 1분 30초쯤 늦어진다. 매시 한 번 보는 분석에는 영향이 없다고 본다.
- job이 실패로 보일 때 어느 수집이 실패했는지는 단계 로그나 포털 실행 이력에서 봐야 한다.
- B(공개)는 미룬 것이다. 공개할 때 Actions 비용 문제도 같이 사라진다.
