# ADR-0014: 가격 신호는 저장하지 않고 API 요청 때 계산한다

- 날짜: 2026-11-04
- 상태: 채택

## 상황

AN-0002와 AN-0004에서 정한 분석 결과를 포털에 처음 넣는다 (#49). 넣는 것은 두 가지다.

- 최저가 변화: 직전 수준 대비 5% 이상 바뀐 최저가가 2번 연속 수집되면 변화로 본다 (AN-0002).
- 판매처 가격 위치: 다른 판매처 가격 중앙값 대비 %(주 기준), 그 판매처 지난 7일 가격 중앙값 대비 %(보조) (AN-0003, AN-0004).

기준은 아직 바뀌는 중이다. 이번 작업 중에도 AN-0005에서 다나와 현금가를 다른 판매처 비교에서 빼기로 바꿨다. 다나와 데이터로 사람이 표시한 정답과 맞춰 보는 재평가는 3~4주 데이터가 쌓인 뒤 한다. 알림 기능은 아직 없다.

## 선택지

### A. API가 요청 때 수집 기록에서 계산

- 좋은 점: 테이블과 마이그레이션이 없다. 기준을 바꾸면 지난 기간에도 바로 새 기준이 적용된다.
- 걸리는 점: 요청마다 7일치 판매처 가격을 읽는다. 로컬 API에서 Neon에 붙여 다나와 상품 하나(판매처 8곳)를 3번 요청한 결과 0.76~0.88초였다. 같은 상품의 가격 이력 요청은 0.41초였다. 상품 목록처럼 여러 상품에 한꺼번에 보여 주려면 느리다.

### B. 수집 때 계산해서 테이블에 저장

- 좋은 점: 화면과 나중의 알림이 저장된 값을 읽기만 하면 된다. 상품 목록에도 붙이기 쉽다.
- 걸리는 점: 기준을 바꿀 때마다 지난 값을 다시 계산하거나, 기준이 다른 값이 섞인다. 테이블과 마이그레이션이 생긴다.

### C. 웹(TypeScript)에서 계산

- 좋은 점: 백엔드를 고치지 않는다.
- 걸리는 점: 같은 규칙을 Python(분석 코드)과 TypeScript에 두 벌 둔다. 분석 노트에서 포털 구현을 그대로 불러 검증할 수 없다.

## 결정

A. 규칙은 `backend/src/flowdeck/signals.py`에 DB를 모르는 함수로 두고, API(`GET /products/{id}/signals`)가 수집 기록을 읽어 부른다. 분석 코드(`analysis/an0005.py`)도 같은 함수를 불러 연습 쇼핑몰 정답과 다나와 데이터에 돌려 봤다.

기준이 아직 바뀌는 중이라 저장된 값과 기준이 어긋나는 일을 피하는 쪽을 골랐다. 이 선택은 Claude가 했다.

## 감수하는 것

- 상품 상세 화면에만 붙였다. 상품 목록에 신호를 보여 주거나 알림을 보내려면 B처럼 저장하거나 수집 작업 끝에 계산하는 단계가 필요하다. 그때 다시 정한다.
- 신호 요청이 가격 이력 요청보다 두 배쯤 느리다(위 측정).
