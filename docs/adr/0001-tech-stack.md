# ADR-0001: 기술 스택

- 날짜: 2026-10-23
- 상태: 채택

## 상황

- 특별히 내세우고 싶은 스택은 없었다.
- 기준은 두 가지였다. 웹 기반이되 앱에서도 연동할 수 있을 것. 데이터 수집과 분석 과정을 제대로 가져갈 수 있을 것.
- 스택은 Claude가 위 기준으로 제안했고, 기준에 맞아서 그대로 채택했다. 아래 선택지 비교는 제안 단계에서 검토한 내용이다. 직접 써 보고 비교한 것은 아니다.

## 선택지

### 백엔드 언어

A. Python

- 좋은 점: 수집(httpx, Playwright)과 분석(pandas, Jupyter)을 같은 언어로 한다. 노트북에서 검증한 분석 로직을 백엔드로 옮길 때 다른 언어로 다시 짤 필요가 없다.
- 걸리는 점: 프론트엔드(TypeScript)와 언어가 달라 타입을 그대로 공유할 수 없다.

B. Node.js(TypeScript) 풀스택

- 좋은 점: 프론트엔드와 언어, 타입을 공유한다. Playwright도 원래 Node용으로 나온 라이브러리다.
- 걸리는 점: 데이터 분석 라이브러리가 Python보다 부족하다. 이 프로젝트는 분석을 중요하게 가져가려 한다.

### 앱 연동 방식

A. API를 먼저 설계하고, 웹은 PWA로. 네이티브 앱은 나중에 여유가 있으면.

B. 처음부터 웹과 네이티브 앱(React Native 등)을 같이 만든다.

- B는 화면을 두 벌 만들어야 해서 범위가 크게 늘어난다.
- 앱에서 연동할 수 있다는 건 공개 API 문서와 PWA로도 보여줄 수 있다고 판단해서 A.

## 결정

| 영역 | 선택 |
|---|---|
| 백엔드 API | Python, FastAPI |
| 수집 | httpx(정적 페이지), Playwright(JS로 렌더링하는 페이지) |
| 분석 | pandas, Jupyter 노트북. 노트북에서 검증한 로직만 백엔드로 옮긴다 |
| DB | PostgreSQL |
| 웹 | Next.js, TypeScript, PWA |
| 실행 환경 | Docker Compose |

결정을 가른 이유:

- 수집과 분석 비중이 커서 백엔드는 Python으로 정했다.
- 웹 포털도 API를 쓰는 클라이언트 중 하나로 둔다. 모바일 앱이나 클라이언트 회사의 다른 시스템도 같은 API에 붙을 수 있다. FastAPI는 OpenAPI 문서를 자동으로 만들어 주기 때문에, 붙일 수 있다는 걸 문서로 바로 보여줄 수 있다.
- 프론트엔드 타입은 OpenAPI 스키마에서 생성해서, 언어가 갈라진 문제를 줄인다.
- PWA로 휴대폰 홈 화면 설치와 푸시 알림을 지원한다.

폴더 구조:

```
backend/    API, 수집기, 스케줄러, 분석 로직
web/        Next.js 포털
analysis/   탐색용 노트북 (분석 노트와 짝)
mock-shop/  데모용 연습 쇼핑몰
docs/       기록
```

## 미룬 결정

- 작업 큐와 스케줄러: 수동 실행과 주기 변경을 실제로 만들 때 비교하고 별도 ADR로 남긴다.
- 배포 환경.
- 네이티브 앱(Expo 등)을 만들지 여부.

## 감수하는 것

- 백엔드와 프론트엔드의 언어가 달라서 의존성, 린트, 테스트 도구를 두 벌 관리해야 한다.
- 백엔드가 따로 있으니 Next.js의 서버 기능은 대부분 쓰지 않는다. 이 용도에는 Next.js가 과할 수 있다.
- Playwright는 브라우저를 띄우기 때문에 메모리를 많이 쓴다. 작은 서버에서는 동시에 돌릴 수 있는 수집 작업 수가 제한될 수 있다.
