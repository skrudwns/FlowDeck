# ADR-0002: 실데이터 소스

- 날짜: 2026-10-23
- 상태: 채택
- 관련: #2

## 상황

- 분석 기능에는 몇 주치 가격 데이터가 필요하다. 그래서 포털과 분석보다 실데이터 수집을 먼저 시작한다 (#2).
- 이번 수집에서 가장 중요한 건 몇 주 동안 끊기지 않고 쌓이는 것이다. 수집 기술을 보여주는 건 이번 목적이 아니다.

## 선택지

### A. 네이버 쇼핑 검색 API

- 좋은 점: 공식 API라 약관 위반이나 봇 차단 걱정이 없다. JSON으로 받기 때문에 쇼핑몰 화면 구조가 바뀌어도 영향이 없다. 키워드 하나로 여러 쇼핑몰의 상품을 받는다.
- 걸리는 점: 키워드 검색 결과가 기준이라 특정 쇼핑몰의 특정 상품 페이지를 지정해서 추적하기 어렵다. 응답 가격이 쇼핑몰 화면의 실제 판매가와 얼마나 맞는지 아직 모른다. 네이버 개발자 센터에 애플리케이션을 등록하고 키를 받아야 한다.

### B. 쇼핑몰 페이지 직접 수집

- 좋은 점: 추적할 상품 페이지를 정확히 지정할 수 있다. 외주 의뢰에서 많이 요구하는 방식이다.
- 걸리는 점: 쇼핑몰마다 이용약관과 robots.txt를 확인해야 한다. 큰 쇼핑몰은 봇 차단이 있고, 화면 구조가 바뀌면 수집이 깨진다. 몇 주 동안 끊김 없이 쌓아야 하는 지금 목적에는 위험이 크다.

## 결정

A. 이번 수집의 목적은 분석용 데이터를 끊김 없이 쌓는 것이고, 끊길 위험이 가장 낮은 쪽이 A다.

직접 수집(B)은 데모용 연습 쇼핑몰(mock-shop)을 대상으로 따로 구현한다. 차단이나 약관 문제 없이 수집 방식을 보여줄 수 있다.

## 확인할 것

결정 시점에 네이버 공식 문서를 직접 열어 보지 못했다. 작업 환경에서 developers.naver.com 접근이 막혀 있었다. 커뮤니티 예시로 확인한 건 응답에 `lprice`, `hprice`, `productType`, `brand`, `maker`, `category1`~`category4` 필드가 있고, 가격이 문자열로 오며 `hprice`가 비어 있는 경우가 있다는 정도다.

아래는 공식 문서와 첫 실제 호출로 확인해서 이 문서에 추가한다.

- 일일 호출 한도, 한 번에 받는 결과 수(`display`)와 시작 위치(`start`)의 최대값
- `lprice`가 무엇의 가격인지 (가격비교로 묶인 상품의 최저가인지, 해당 판매처의 가격인지), `productType` 값의 의미
- 같은 상품을 수집 시점마다 같은 ID로 식별할 수 있는지

## 감수하는 것

- 추적 단위가 "키워드 검색 결과에 나온 상품"이다. 경쟁사의 특정 상품 하나를 지정해서 추적하는 시나리오와는 차이가 있다.
- 네이버 쇼핑에 노출되는 상품만 수집할 수 있다.
- 네이버가 API 정책을 바꾸면 영향을 받는다.
