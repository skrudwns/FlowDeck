# ADR-0010: 연습 쇼핑몰(mock-shop) 구조와 수집

- 날짜: 2026-10-25
- 상태: 채택
- 관련: #15, ADR-0004, ADR-0005, ADR-0006, ADR-0007

## 상황

- 다나와에서 모은 원본 데이터는 공개하지 않는다 (ADR-0004 수집 원칙 6). 공개 데모에 보여줄 가격 데이터가 따로 있어야 한다.
- 다나와 수집은 정해 둔 pcode 목록의 상품 페이지만 받는다. 목록 페이지를 돌며 상품을 찾아내는 크롤링은 아직 보여준 적이 없다.
- 가격을 어떤 규칙으로 바꿨는지 알고 있는 데이터가 있으면, #13 분석에서 급락이나 요일 패턴을 제대로 찾는지 맞춰 볼 수 있다.

## 선택지: 쇼핑몰을 어디서 띄우나

### A. 수집 작업 안에서 띄운다

GitHub Actions 수집 작업이 쇼핑몰 서버를 잠깐 띄우고 localhost로 수집한다.

- 좋은 점: 계정, 비용, 배포 설정이 없다. 수집 코드는 공개 서버를 수집할 때와 같다 (HTTP 요청, robots.txt, 요청 간격).
- 걸리는 점: 방문자가 쇼핑몰 페이지를 인터넷에서 직접 볼 수 없다.

### B. 무료 호스팅에 배포한다

Render 같은 곳에 올리고 공개 주소를 수집한다.

- 좋은 점: 방문자도 쇼핑몰을 볼 수 있다.
- 걸리는 점: 계정 가입과 설정이 필요하다. 무료 서버는 쉬다가 첫 요청에 깨어나서 느리다.

### 결정

A. 사용자가 골랐다. 공개 배포는 포털 데모를 배포할 때 같이 정한다.

A가 되려면 가격이 서버의 실행 상태가 아니라 "상품, 판매처, 시각"만으로 정해져야 한다. 서버를 매시간 새로 띄우기 때문이다. 그래서 가격은 규칙 함수로 계산하고, 난수 대신 `sha256(상품, 판매처, 날짜)` 같은 값으로 정한다. 언제 어디서 띄워도 같은 시각이면 같은 가격이 나온다.

아래는 사용자가 따로 고르지 않았고 Claude가 정했다.

## 쇼핑몰

- 저장소의 `mock-shop/` (ADR-0001 폴더 구조). 백엔드와 별도 uv 프로젝트로 둔다. 수집기 코드와 섞이지 않게 하고, 나중에 따로 배포할 수 있게 한다.
- FastAPI + uvicorn. 백엔드에서 이미 쓰는 도구라 새로 배울 것이 없다. HTML은 문자열로 만든다. 페이지가 둘뿐이라 템플릿 엔진을 붙이지 않는다.
- 여러 판매처가 한 상품을 파는 가격 비교 사이트 형태로 만든다. 다나와와 같은 저장 구조(최저가, 판매처 수, 판매처별 가격)에 그대로 들어가고, 포털 화면도 그대로 쓸 수 있다.
- 페이지 구조는 다나와와 다르게 만든다. 다나와 파서를 재사용하지 않고 수집 대상마다 파서를 따로 두는 구조를 보여주기 위해서다.

| 경로 | 내용 |
|---|---|
| `/robots.txt` | `/admin/`만 막는다. 수집기가 robots.txt를 읽고 지키는지 확인할 수 있다 |
| `/products?page=N` | 상품 목록. 한 페이지에 5개, 다음 페이지 링크 |
| `/products/{id}` | 상품명, 판매처별 가격·배송비·재고 |

### 가격 규칙

시각은 한국 시간 기준, 1시간 단위로 바뀐다 (수집이 1시간에 한 번이라 그보다 잘게 바꿔도 보이지 않는다).

- 기본가: 상품·판매처마다 정한 값.
- 일별 변동: 날마다 기본가의 -3% ~ +3%. 100원 단위.
- 요일 할인: 판매처 하나는 토·일에 10% 내린다.
- 급락: 상품·판매처·날짜마다 1/7 확률로, 그날 정해진 3시간 동안 25% 내린다.
- 품절: 상품·판매처·날짜마다 1/10 확률로 그날 정해진 6시간 동안 품절. 상품마다 품절되지 않는 판매처를 하나 둬서 상품 전체가 품절되지는 않게 한다. 전체 품절까지 다루려면 저장 상태와 화면을 더 고쳐야 해서 이번에는 뺐다.

규칙과 확률은 데모에서 한 주 안에 각 패턴이 몇 번씩 보이도록 잡은 값이다. 실제 쇼핑몰을 본떠 정한 값은 아니다.

규칙을 어떻게 적용했는지는 쇼핑몰 코드의 함수로 돌려받을 수 있게 한다. 분석 노트에서 이 함수로 정답을 만들어 결과와 비교한다. 실제 쇼핑몰에는 없는 정보라 HTTP로는 내보내지 않는다.

## 수집

- 수집 대상 이름은 `mockshop`. 다나와와 같은 테이블에 `source`로 나눠 저장한다.
- 상품 목록은 파일로 정하지 않고 목록 페이지를 다음 페이지가 없을 때까지 돌며 찾는다. 찾은 상품은 추가하고, 목록에서 사라진 상품은 비활성화한다 (다나와 대상 목록 맞추기와 같은 규칙). 목록 페이지 수집이 실패하면 그 실행은 실패로 기록한다.
- 요청 간격, robots.txt, 403·429에서 멈추기는 다나와와 같은 코드를 쓴다 (ADR-0004 수집 원칙 2, 4, 5). 그래서 다나와 클라이언트에서 이 부분을 떼어 낸다.
- 실행 위치: `collect.yml`에 쇼핑몰 수집 작업을 다나와 작업과 나란히 추가한다. 같은 cron-job.org 호출(매시 17분, ADR-0006)로 둘 다 돈다. 작업이 나뉘어 있어서 한쪽이 실패해도 다른 쪽은 돈다. (2026-10-25 ADR-0012에서 한 job으로 합쳤다. 다나와가 실패해도 연습 쇼핑몰이 도는 건 유지했다)
- 감시: Healthchecks 체크를 따로 둔다 (`MOCKSHOP_HEALTHCHECK_URL`). 같은 체크를 쓰면 어느 쪽 문제인지 알 수 없다. 판정 기준은 ADR-0007과 같다.

## 저장 구조 변경

- `collection_runs.source` 추가. 실행 기록이 어느 수집 대상의 것인지 알아야 포털 작업 목록에 작업별 마지막 실행을 붙일 수 있다. 기존 행은 모두 다나와라 `danawa`로 채운다.
- `seller_prices.in_stock` 추가. 품절인 판매처도 "품절"이라고 페이지에 나온 사실을 저장한다. 목록에서 빠진 것만으로는 품절인지 파싱이 잘못된 건지 구분할 수 없다. 다나와 행은 모두 `true`.
- 최저가와 판매처 수는 재고가 있는 판매처만으로 계산한다.

## 감수하는 것

- 쇼핑몰 서버를 매시간 띄우는 시간만큼 Actions 사용 시간이 늘어난다. 저장소는 비공개라 이 시간은 월 포함 사용량(GitHub Pro 3,000분)에서 빠진다. 처음에는 여기에 "공개 저장소라 무료 한도 걱정은 없다"고 잘못 적었다 (아래 돌아보기, ADR-0012).
- 백엔드 파서 테스트의 쇼핑몰 HTML 예시는 쇼핑몰 코드에서 만든다. 쇼핑몰 HTML을 바꾸고 예시를 다시 만들지 않으면 테스트는 통과하는데 실제 수집은 실패할 수 있다. CI에서 예시를 다시 만들어 달라졌으면 실패시킨다.
- 규칙으로 만든 가격이라 실제 시장 데이터의 잡음이나 경쟁 반응은 없다. 분석 알고리즘이 쇼핑몰 데이터에서 맞는다고 다나와 데이터에서도 맞는다는 보장은 없다.

## 돌아보기

### 2026-10-25: 저장소가 공개라고 잘못 적었다

- 감수하는 것에 "공개 저장소라 무료 한도 걱정은 없다 (ADR-0003)"고 썼다. 저장소 공개 여부를 확인하지 않고 쓴 문장이다. ADR-0003은 비공개 저장소의 월 2,000분 기준으로 계산하고 있었다.
- 같은 날 기록을 점검하다가 저장소 페이지에서 Private을 보고 알았다. 계정은 GitHub Pro라 포함 사용량이 3,000분이다.
- #15, #16으로 매시 job이 1개에서 3개가 되어 한도에 닿을 수 있었다. 수집 워크플로를 한 job으로 합쳤다 (ADR-0012).
- 비용이나 한도를 근거로 쓰는 문장은 계정과 저장소 설정을 직접 확인하고 쓴다.
